## 1. 能力清单与应用场景

| 能力 | 一句话说明 | 典型场景 | 成熟度 |
| --- | --- | --- | --- |
| Agent 循环（agent-loop） | 接收消息→调模型→执行工具→回填结果→循环直到完成，全程事件流输出 | 任何"AI 员工干活"的场景：聊天、定时任务、子代理派工 | 已实现，TriLC 生产在用 |
| 工具注册表 | 宿主把工具注册进来，模型按名字调用；内核零内建工具 | TriLC 注册 shell_exec；TriPilot 客户端回环执行编辑类工具 | 已实现 |
| 六模式权限引擎 | default / acceptEdits / dontAsk / plan / auto / bypassPermissions + 规则（allow/deny/ask）+ 敏感路径安全检查 | 企业内可控放权：plan 模式只读评审、dontAsk 限定目录自动干活、交互确认高危命令 | 已实现，规则格式兼容 CC |
| 四层级代理准入 | main / heartbeat / subagent / coordinator 四档工具权限 + 反递归守卫 | 定时任务代理只能写文件不能跑 shell；子代理只读不越权 | 已实现 |
| cron 调度核 | at/every/cron 三种调度、整点错峰、原子持久化、失败退避、心跳降噪 | 周平面任务、心跳巡检、定期汇总类员工任务 | 已实现，含 Windows 鲁棒性修复 |
| 子代理生成 | 一条命令拉起受限子代理跑子任务，事件流回传 | "让小贾查一下" → 主代理 spawn code_explorer | 已实现 |
| 员工合同校验（contracts v3） | 校验 .contract.yaml 岗位合同：身份/路径/职责/决策权/协作关系/工具风险/输入输出 | 13 名 AI 员工入职定义的机读真源；双域（TriLC/TriMC-TriRMC）统一解析 | 已实现，strict 无向后兼容 |
| 消息守卫 | 拦截无正文无工具调用的"空头"回复污染会话历史 | DeepSeek 类推理模型只吐思维链时的兜底 | 已实现 |
| 进程监督器 | 子进程双超时/SIGKILL/GBK 乱码修复/黑窗抑制 | shell_exec 类工具的生产级托管 | 已实现 |

**明确不属于它的**：具体工具集（宿主注册）、会话持久化与恢复（宿主做，如 TriLC 的 SQLite 会话库）、上下文压缩（宿主外包裹）、密钥管理（宿主域）。这是理解产品边界的关键——它是"发动机"，不是"整车"。

## 2. 在 TriMetaverse 产品栈中的位置：M/R 双面图

公司形态是"一个主控面 + 多个本地执行面"。M 面 = Main Controller 服务域（TriMC 现役，向 TriRMC 迁移中）；R 面 = Local Controller 执行节点（TriLC daemon，装进用户机器，随 TriCade 分发）。agent-core 是两面共用的同一颗内核：

```mermaid
graph TB
    subgraph 用户触达
        TC["TriCade 桌面端"] --> TP["TriPilot VS Code 扩展"]
    end
    subgraph R面·本地执行节点
        TP -->|"HTTP /v1/messages"| LC["TriLC daemon (127.0.0.1:8711)"]
        LC --> KERNEL["@tricompany/agent-core v0.1.0"]
        LC --> DB["本地 SQLite 会话库"]
    end
    subgraph M面·服务主控
        MC["TriMC 现役主控 → TriRMC 迁移中"] --> KERNEL2["同一个 agent-core"]
        MC --> PG["观测 PG / 编排 / config-sync"]
        LC <-->|"心跳 / 任务下发 / 结果回传 / 离线重放"| MC
    end
    KERNEL -.->|"trimodel 统一模型注册表"| MODEL["DeepSeek 系模型（tmv-* 路由）"]
```

读图要点：

- **同一颗内核，两种装配**。R 面轻装：TriLC 不加载 Soul Loader / Memory Injector 等 pipeline 服务（`TriLC/src/server/app.ts:10-11` 头注释明说），裸用 agentLoop；M 面全装：TriRMC 以薄壳 DI 层把 context-builder/prompt-cache/tool-gater 注入同一个循环（`TriRMC/src/agent-loop/loop.ts:1-16`）。用户在两端得到行为一致的 agent 能力，深度不同。
- **迁移语境**：七大件种子资产正从 TriMC 向 TriRMC 双跑迁移（`TriRMC/MIGRATION.md`），其中 agent-loop/cron/contracts 三件的核心就在本包——所以内核升级直接影响 M/R 两面的演进节奏。
- **模型面**：内核通过 trimodel 抽象接模型，默认 deepseek-v4-pro，带 tmv-* 路由链与两层回退（详见 04 §4）——这与原版 CC 绑定 Claude 模型族是根本差异。

## 3. 与直接用 Claude Code 的差异和取舍

| 维度 | 直接用原版 CC | 用 agent-core 自研内核 | 取舍判断 |
| --- | --- | --- | --- |
| 模型绑定 | Claude 模型族，窗口/价格随 Anthropic | trimodel 注册表，DeepSeek 系可自路由、可降级 | 自研换来模型自主权与成本控制 |
| 部署形态 | 单机 CLI/IDE 伴生 | daemon 化：R 面常驻本地、M 面服务化编排 | 支撑"赛博公司多节点协同"的产品形态 |
| 权限体系 | 内置六模式+规则（闭源 vendor） | 同构重实现（吸收 CC 2.1.88 规则格式），且可审计、可改 | 行为对齐降低迁移成本，代码自主可控 |
| 会话持续性 | SendMessage resume 全量 transcript 回灌 + auto-compact 有损压缩 | 无内建恢复；公司路线走记忆外置 + 收口落盘重生 | 规避累积爆窗/熔断/缓存全 miss（依据创新记录 §2-3），代价是宿主要自建持久化 |
| 上下文压缩 | auto-compact 内建（阈值约 967K） | 内核不含；TriLC 外包裹（90K 阈值、最多重启 3 次） | 决策权上收到宿主，策略可按部署定制；内核保持薄 |
| 员工治理 | agents/skills 文件约定 | contracts v3 机读合同：决策权/协作关系/工具风险/IO 全结构化 | 从"提示词工程"升级为"组织工程"，支撑 13 员工编制 |
| 工具生态 | 大量内建工具 | 零内建、纯注册表 | 每个消费方按需组装；起步成本高、失控面小 |
| 成熟度 | 生产打磨数年 | v0.1.0，已知缺口清单公开（见 04 §15） | 明确的差距诚实标注，不吹 parity |

一句话总结取舍逻辑：**原版 CC 是给个人开发者的单机工具；公司要的是多节点、可审计、模型自主的组织化 agent 基础设施——所以核心机制对齐、架构路线分叉。**

## 4. 典型使用流程走查

### 场景 A：用户在 TriPilot 里发一句"帮我看看这个仓库的结构"

1. TriPilot 把消息以 Anthropic Messages 格式 POST 到本机 TriLC `/v1/messages`。
2. daemon 组装参数：tier=main、权限模式（请求可带 permission_mode，或环境变量缺省）、plan 门禁依赖注入（`app.ts:1874-1893`）。
3. agent-core 循环开转：模型回复工具调用（如 glob_search）→ 注册表执行（客户端回环类工具返回占位、daemon 本地工具真执行）→ 结果回填 → 直到模型给出文本总结。
4. 过程中以 SSE 流式回写 TriPilot 渲染；最终回复过消息守卫后落本地会话库。

### 场景 B：周日晚上 23 点的周平面定时任务

1. cron job 按 `cron` 表达式配置，存于 `$TRIMC_CONFIG_DIR/cron/jobs.json`。
2. JobExecutor 扫描到期任务执行 handler；整点类任务自动获得错峰偏移，避免和其他整点任务挤在一起。
3. 任务绑定的岗位若未在岗，调度门禁拦截并埋 routing_error 指标（`app.ts:876-886`）。
4. 失败进入 consecutiveErrors 计数与退避策略；心跳策略决定要不要打扰人——连续正常的"一切 OK"心跳被抑制不投递。

### 场景 C：主代理说"让小贾检查这段代码"

1. 主代理（main 层）调用子代理生成，spawn 出受限实例（默认 subagent 层：只读工具、最多 10 轮、不可再生子代理）。
2. 子代理的事件流被翻译回主循环可见的 tool_result。
3. 结束即释放——没有跨任务的会话累积，员工的长期记忆在文件资产里不在会话里。

## 5. 产品侧常见误区

1. **"装了 agent-core 就有了一整套 AI IDE"**——不是。它是内核，工具、界面、存储、模型密钥全是外围组装件。
2. **"它能像 CC 一样接着上次的会话继续聊"**——内核无此能力；现役产品的会话恢复是 TriLC 会话库做的，跨任务连续性靠公司的收口落盘制度而非会话本身。
3. **"权限模式和 CC 完全一致可以照搬配置"**——模式名与规则格式兼容，但工具名体系是本内核自己的（read_file/shell_exec 等），CC 名靠别名表映射，混用时以映射结果为准。
4. **"v0.1.0 已经功能对齐 CC 2.1.88"**——没有。已知缺口如实列在 04 §15，评审需求时先过那张表。
